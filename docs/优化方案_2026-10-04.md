## 摘要

我先量了家底，不凭印象开方子：

| 指标 | 现状 | 问题 |
|---|---|---|
| `pingpong_game.gd` | **5286 行 / 370 个成员变量** | 占全部代码 30%，一个文件揉进了物理、规则、AI 调度、HUD、发球解算、输入、结算 |
| `game_state.gd` | 2700 行 / 42 变量 | 存档、经济、任务、排位、赛事、音频设置全在一个 autoload 里 |
| 难度参数 | **30 个 `easy_/normal_/…/master_` export** | 每个参数手工写 5 份，靠 **10 处 `_tier5()` 手写分派**填进去 |
| 场景节点 | 424（已合批） | 无 |
| Web 包 | 28MB | 无 |

**两个核心结论：**

1. **结构问题的主因不是「文件长」，是「难度系统用 30 个平行变量 + 10 处手写分派表达」。**
   想调 AI 强弱，你得同时想清楚改哪 30 个变量、哪 10 个分派点；漏一处就出现「反应速度上去了但回球质量没变」这种
   「难度好像没变」的怪事（`MEMORY.md` 里那条「凶度只乘扣杀概率」的注释就是历史证据）。

2. **手感问题的主因不是「数值不准」，是「难度曲线是 5 个离散的点，没有连续可控性」**，
   而游戏内部已经**实际在用连续难度**（排位段位喂 `set_difficulty_t()` 浮点），
   也就是说连续性是**后加的、补丁式的**，底层的 5 档插值没有为它设计。

## 一、代码结构优化

### 1.1 难度系统：30 变量 × 5 档 → 一张表

**现状**

```gdscript
# 声明：30 个 export，每个 5 份
@export var easy_flight_time: float = ...
@export var normal_flight_time: float = ...
@export var hard_flight_time: float = ...
@export var expert_flight_time: float = ...
@export var master_flight_time: float = ...

# 使用：10 处手写分派，每处一个函数
func _flight_time() -> float:
    return _tier5(easy_flight_time, normal_flight_time, hard_flight_time,
        expert_flight_time, master_flight_time)
# ...还有 9 处
```

**问题**（都是实际踩过的）

- 加第 6 档要改 30 个声明 + 10 个分派函数，共 40 处；
- `hard_` 打错成 `had_` 编译会报错，但**顺序写反**（`hard` 和 `expert` 互换）编译全绿、
  跑起来只是「大师档比专家档弱」，极难发现；
- 调平衡时无法「只调反应速度不调回球质量」——它们被平铺在同一命名空间，靠命名约定区分。

**改法**

```gdscript
# 一张表：key 是参数名，值是 5 档（或用 Curve 表达连续曲线）
const DIFFICULTY_PROFILES := {
    "flight_time":      [1.05, 0.92, 0.80, 0.70, 0.62],
    "spread":           [0.14, 0.11, 0.085, 0.065, 0.05],
    "reach_scale":      [0.86, 0.94, 1.02, 1.09, 1.15],
    # ...
}

## 连续难度：整数档逐位不变（硬约束，探针必须验）
func tune(key: String, t: float) -> float
```

`t` 取整数时 `tune()` 必须**逐位等于**原来那一档 —— 这条已有先例
（`rank_difficulty_t()` 的同类约束已实测过），探针会照抄那个验法。

**收益**：加档从 40 处降到 1 处；平衡调参变成改一张表；
顺手能做「难度曲线可视化」把 5 个点画出来看是否平滑。

**风险**：★★ 高。这是核心数值来源，改错会毁掉所有已调好的手感。
**必须逐位回归**：30 个参数 × 5 个整数档 = **150 组断言**，全部与改前逐位比对。

### 1.2 拆 `pingpong_game.gd`（5286 → 约 4 个模块）

**切分依据是「状态归属」，不是行数均分。** 现在的模块边界其实已经写在注释里了，只是没兑现：

| 抽出模块 | 依据 | 现状行数区间 | 理由 |
|---|---|---|---|
| `serve_system.gd` | 「发球：抛球 / 合规发球 / 轨迹提示」三个连续注释段 | 1626–2519（**~890 行**） | 已经是独立子系统，只是寄生在主控里。有自己的状态机（`_serve_phase`/`_serve_block`）、自己的解算（`_solve_legal_serve`）、自己的可视化（`_build_serve_traj`） |
| `rally_hud.gd` | 「连拍爽感循环」 | 1067–1142 + 4760–4925 | HUD 构建 + 每帧更新自成一体，视觉与逻辑耦合松 |
| `opponent_ai.gd` | 对手/队友的全部排定与击球 | 3311–3825（**~515 行**） | 与玩家挥拍（2802–3300）几乎不共享状态，天然可分 |
| `match_referee.gd` | 判分与收尾 | 3826–4443（**~620 行**） | 注释明写「`_finish()` 是唯一收口点」—— 收口逻辑该独立成裁判模块，而不是散在主控里 |

抽完主控剩约 **3200 行**（物理推进、玩家挥拍、输入、场景引用、生命周期）。

**为什么是这个顺序**：这四块的边界最清晰、跨块依赖最少。
`match_referee` 排第一是因为它最重要（判分错 = 整个游戏错）。

**收益**：改判分逻辑不用在 5286 行里找；改发球不影响对手 AI。

**风险**：★★ 中高。**跨模块状态是主要风险**——`_serve_phase` 被 `rally_hud` 读、
`rally_hits` 被 referee 读、对手 AI 读玩家的拍面位置。
**做法**：用「引用传递」而不是「复制状态」——模块持有主控的引用，只读不算。
**不做**的事：不引入 autoload（记忆里已有 autoload 写真实存档的坑）。

**必须先做的准备**：**先补一份覆盖当前行为的回归探针，再动手拆。**
现在没有这样的探针，拆完无法证明「行为没变」。
这是整个方案里**优先级最高的一项** —— 没有它，后面所有重构都不可验证。

### 1.3 `game_state.gd` 拆分（2700 行）

`Game` 承担了 7 个互不相干的关注点：存档、金币经济、每日/每周任务、排位、赛事、音频设置、球拍皮肤。

搬动它们的风险远大于收益。等前两项落地后再评估。

**风险**：★★ 中。`reset_all()` 曾经漏清整届联赛，拆分时要确保不重犯。

## 二、游戏手感与平衡

### 2.1 难度曲线目前是「5 个点」，不是「一条线」

**现状**（这是我实测过的数据，来自记忆里的记录）

接发球**对手直接得分率**：

| 档位 | 得分率 |
|---|---|
| 简单 | 4.08% |
| 普通 | 1.92% |
| 困难 | 1.08% |
| 专家 | 0.54% |
| 大师 | 0.22% |

**这条曲线有两个问题：**

1. **简单档 4% 也偏高。** 乒乓球新手被「白送分」打 100 局会有 4 次莫名其妙丢分，
   而且**他看不出为什么**（发球明明过网了）。这是挫败感的直接来源。
2. **高档衰减太快（0.54% → 0.22%），玩家感觉「大师和专家没区别」。**
   1/0.54 : 1/0.22 = 3.4 : 1，但玩家的主观感受远小于此，因为高档的差异
   被「更小的失误率」掩盖了 —— 玩家赢得多，**感觉不到 AI 变强了**。

**改法（两条，都可量化验证）**

- **A. 修简单档的天花板**：把「简单」的发球直接得分压到 **1.5% 以下**。
  已知的正确杠杆：`serve_return_miss_scale`（现 0.12）、
  `serve_return_out_scale`（现 0.25）、`opp_serve_reach_bonus`（现 1.25）。
  ★ 改 `opp_serve_reach_bonus` 要守**不等式** `接发球够球半径 > 发球瞄准跨度`
  —— 现在是 `0.66 × 1.25 = 0.825 > 0.724`，缩小这个倍数会让两端重新出现「瞄哪儿就白送分」的死区。
- **B. 拉开高档的「可感知差」**：大师档不该只是「失误更少」，
  应该加点**玩家能看见的东西** —— 比如接发球抢冲（提前下板）、
  变线球占比提高、对手移动更快但**回球更狠**。让高档的强度体现在画面上而不只是分数上。

**验证方式**：批量跑发球落点采样（记忆里已有这套采样工具，18 个落点的回归），
统计每档 1000 次发球的直接得分率，**写进探针断言**。

### 2.2 「凶度」机制有半成品，值得补完

`_opp_rage()`（3484 行）现在**只乘在扣杀概率上**。记忆里记着这是**刻意的**：

> 凶度只乘在扣杀概率上，不动反应速度/回球质量 —— 否则玩家以为难度变了。

这个判断是对的（玩家感知的是「AI 变凶了」不是「AI 变聪明了」）。
但现在凶度没有任何**玩家可见的反馈** —— AI 变得更有攻击性，玩家只会觉得「运气不好」。

**建议**：加一条 HUD 提示（如对手连续得分时屏幕边缘泛红 / 记分牌出现「对手进入状态」字样）。
这是纯反馈层改动，不碰任何数值，**风险最低、感知收益最高**。

### 2.3 体力系统的净效果需要实测确认

记忆里记着：`stamina_regen 9.0` / `cost_per_hit 5.0` / `regen_delay 1.10`，
以及「净下降取决于回复速度 vs 出拍节奏，只看单拍消耗会被回复抵消」。

**方案**：写一个探针模拟「不同连拍节奏下的体力轨迹」，
量出「什么样的打法实际会掉体力」。如果结论是「只有连续快攻才掉」，
那当前的数值就是对的、不用改；如果发现「无论怎么打都不掉」或「怎么打都掉」，
才是需要调的地方。**先量再改，不要凭印象调数值。**

### 2.4 难度可调性：让玩家自己调

难度只有 5 档 + 排位段位自动喂。中间没有余地。
`_diff_t` 已经是浮点了，**技术上是连续的**，但自由对战里没有入口。

**建议（可选，风险最低的可见改进）**：自由对战面板的难度行加一个
「精细微调」滑杆（`_diff_t` 从 0~4 连续），显示为「普通 +0.3」这种形式。
成本几乎为零（`_diff_t` 和 `set_difficulty_t()` 都已经支持浮点），
但让玩家在「大师太难/专家太简单」时有出路 —— 这是难度离散化最典型的挫败点。

   （约 200 组断言），全量行为快照则慢很多。
